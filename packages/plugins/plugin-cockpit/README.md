# Cockpit (`partnersinbiz.cockpit`)

One place to run the company: what waits on you, what the agents did, money, pipeline, marketing, delivery, agent cost and quality, and system health. The Cockpit also owns the company's team roles: the **Operator** (chief of staff), the **Reviewer** (quality reviewer) and the optional **Acceptance** tester.

- Plugin key: `partnersinbiz.cockpit` (kit `COCKPIT_PLUGIN`)
- Namespace: `plugin_cockpit_b8a99e8b16` (slug `cockpit`)
- Page: `/<company>/cockpit` (tabs Overview, Flows `?tab=flows`, Profile `?tab=profile` and Memory `?tab=memory`) · sidebar "Cockpit" (order 5, above Setup; its count turns red for money or legal) · dashboard widget "Company today". The team is staffed in **Setup → Team** (`/setup?section=team`); an old `?tab=team` link is sent there.
- Settings must be saved once per company: the jobs **and** the event handling (answers to questions, onboarding, the CRM client copy) only act for companies with saved Cockpit settings. The exception is `company.created`: the new-company bootstrap works without them.
- Version 0.6.4 (migrations 001 to 007, none new). 0.6.4: every journey's first step passes this run's id to `create-canary-client` (`runRef`, needs CRM 0.14.2) and expects it echoed, so an answer recorded from an earlier call or the previous journey fails step 1 (all journeys moved up one version). 0.6.3: lead capture v2 (the Inbound Qualifier, which owns the lead issue and has it checked out, closes it; the journey waits and checks instead of closing it itself), and the Acceptance skill says every journey starts with a new create-canary-client call. 0.6.2: one open acceptance run per company, whatever the journey (they share one canary client and each ends by removing it; the first live three-journey request lost the canary under two of them), and the skill says to run them one after another. 0.6.1: the acceptance record step reads an evidence item's file, command, link or text from `ref` or the names an agent naturally uses (`path`, `file`, `url`, `link`, `command`, `text`) and says in the failing check when items were ignored; the Acceptance skill shows the exact evidence shape (the first live run lost a screenshot to `path`). 0.6.0: two more acceptance journeys on the canary client, `esign` (a document prepared, read back and sent for signature as an approval that reaches the Reviewer first, then withdrawn) and `site-events` (a key, one test event to the public endpoint, the daily counter moves, the key is paused), both run by a release of the CRM and on demand; a journey step may name the issues a rehearsal opens (`cleanupIssues`), which the Cockpit cancels with the canary's approvals when the run ends; the metric-key help an agent reads when it sets a goal now names the CRM's website, attribution and e-sign numbers. 0.5.5: company-os asks for a grant with kind grant; ## How it works

1. **Projection.** The plugin subscribes to `plugin.<key>.cockpit.snapshot` and `plugin.<key>.setup.status` for every PiB plugin. It keeps the newest report per company, plugin and kind in `snapshots`, in one upsert. An older `checkedAt` never replaces a newer one. The subscription decides which plugin a report belongs to.
2. **Page (Overview).**
   - **Today:** a summary line plus a health light, which shows the worst status across all plugins.
   - **Waiting on you:** merges several sources and removes duplicates by key and by issue. Questions agents asked the owner come first (money and legal red, the rest amber, with age, the question, the options and an **Answer** link to the issue), then money and legal, then oldest first within each kind. The sources are:
     - open questions from `ask-owner` (`cockpit.load` → `asks`)
     - every plugin's `waiting` items, taken live from `GET /api/plugins/<key>/api/cockpit` for plugins that are installed, ready and switched on, or from the projection when a plugin cannot answer
     - open issues with no assignee, older than a day: one item with the count and the first five as links (`cockpit.load` → `unassigned`)
     - open approvals (`/api/companies/:id/approvals`)
     - your open issues (`/issues?assigneeUserId=me&status=todo,in_progress,in_review,blocked`)
     - Setup's missing required items (links to `/setup`)
   - **Flows:** the company graph in one card: the sentence from the Flows tab and each flow as a row of dots (amber stuck, module colour busy, dashed off), linking to the flow on the Flows tab.
   - **Money / Pipeline / Marketing / Delivery:** the plugins' KPIs, grouped.
   - **What the agents did:** 24 hours or 7 days. Combines plugin activity, host activity (`/activity`) and runs (`/heartbeat-runs`), grouped by agent.
   - **Agents:** each agent's status, last run, runs in the last 7 days, and spend against budget this month. Spend and budget come from the agent record, overridden by `costs/by-agent?from=<month start>` and the agent's monthly `budgets/overview` policy. Quality metrics come from the snapshots. A chip appears at 80% of budget or when the agent is in error.
   - **System health:** every plugin's checks, worst first, each with its fix and a link. A check that links to Setup → Team (an empty, paused or failing Operator or Reviewer) says **Fix in Setup**. Adds "plugin not reporting" when a plugin that is switched on has sent no snapshot for 3 hours. Shows the last database backup from `GET /api/health` (`databaseBackup.latestBackup`) and warns when it is more than 3 hours old.
   - Modules switched off in Setup (kit `setup-client` `fetchModules`) are hidden.
3. **Team (in Setup → Team).** The Cockpit has no Team tab. Setup → Team hires, picks, changes or removes the Operator and Reviewer through the Cockpit's actions (`cockpit.hire-options`, `cockpit.start-hire`, `cockpit.save-team`, `cockpit.load` for `team` and `roles`), and sets the owner and the review switch.
   - **Save:** emits `roles.updated` (kit `RolesPayload`).
   - **When an agent is linked:** it gets a `tools:use` grant for plugin tools and its managed skill (`pib-operator` / `pib-reviewer`). For the Operator, the Cockpit also creates or reassigns the two routines.
   - **Overview:** "No Operator yet" and the Operator / Reviewer health checks link to Setup → Team ("Fix in Setup").
4. **Jobs.** All of them only act for companies with saved Cockpit settings (host rule), each naming its company explicitly.
   - **`reemit-roles`** (`10 * * * *`): sends the roles again and links any pending hires.
   - **`health-alerts`** (`20 * * * *`): keeps one **System health** issue per company. The issue covers bad checks, plugins that are not reporting, agents in error or at 80% or more of budget, and the operations watch below (failing routines, agents that fail too often or the same way, issues that keep failing, issues blocked or stalled with nobody to move them) and the 0.5.0 checks (see "Health" below). It is assigned to the Operator when one is linked, otherwise to the owner. The assignee is woken only when a new problem appears (problems are keyed by agent, issue or routine, so a changed count updates the issue in place). The issue closes when everything is ok. Set `healthIssue: false` to turn it off. The same pass settles questions whose reply was missed, re-announces answers whose effect has no result, opens the Cockpit's own questions (memory grant, goals), repairs unrouted approvals and sweeps every company's managed skills.
   - **`memory-upkeep`** (`30 1 * * *`), **`credentials-check`** (`50 3 * * *`), **`closeout-sweep`** (`20 4 * * *`), **`improvements-recheck`** (`40 4 * * *`) and **`business-review`** (`30 4 * * 1`): see the 0.5.0 sections below.

## Flows (the company graph)

Cockpit → **Flows** (`?tab=flows`) draws every flow in kit `FLOWS` (lead to cash, onboarding, content, campaigns, books, payroll) stage by stage, in order. Pure logic in `src/flows.ts`, drawing in `src/ui/flows.tsx`.

- **Numbers:** each plugin's snapshot `flows` (kit `FlowStageReport`), live first, else the stored copy. Parsing keeps only known stages the sending plugin owns, once each, with whole, non-negative numbers (stuck never above the count); older plugins send none and their stages show "–".
- **Each stage:** its count (and amount when reported), stuck items with the plugin's reason, and who it waits on: the role's agent by name, "You", the customer or "Automatic". It links to the stage's page (with the company prefix).
- **Switched off**, first cause wins: the module is off (Setup modules) → the plugin is not installed or not ready → its settings are not saved (the stored setup status's `settings` item; no status at all means not saved, as Setup assumes; the Cockpit uses its own saved flag) → its role has no running agent (the snapshots' `team`, the Cockpit's Operator and Reviewer, statuses from the agents list; kit `roleAgentUsable`). An off stage is muted with its reason and **Fix in Setup** (`teamSetupPath(role)`, the Setup checklist at the module, or Setup modules).
- **Top of the tab:** one sentence ("4 of 6 flows are running; 3 stages are switched off: no Account Manager (2) and Mailbox settings not saved (1).") and the fixes grouped, biggest first.
- **Stuck first:** "Stuck now" lists every stuck stage grouped by who it waits on (you, agents, customers, the system), worst first (most stuck, then the oldest); flows with stuck work come first. On a phone the list shows five, then "Show all", and flows without stuck work start folded.
- **Layout:** a line of stations when the card is wide enough for the flow's stages (container queries), a vertical line on phones and narrow cards.
- **The Cockpit's own stages** (in its snapshot `flows`): `onboarding.open` = open onboarding issues (origin kind `plugin:partnersinbiz.cockpit:onboarding`, not done or cancelled), stuck when open for more than 7 days; `onboarding.grants` = open `ask-owner` questions of kind `grant`, stuck when asked more than 3 days ago (the stale-question age).
- **The Operator's brief:** `company-brief` → `stuckFlows`, the top 5 stuck stages (same order and numbers), with who each waits on and a link.

## Done-checks

Kit done-checks (`runDoneCheck`, run from the Cockpit's one `issue.updated` handler: a second subscription to the same event would make the host deliver every event twice): when an **agent** closes one of these issues, the Cockpit checks the work; unfinished work reopens (`todo`) with what is missing and the agent is woken; the third early close goes to the Operator. A person's close is never checked.

| Origin id prefix | Done when | Finished another way |
|---|---|---|
| `cockpit:onboarding:` (and `onboarding:` from before 0.4.0) | every `- [ ]` line of the checklist is ticked (`- [x]`); the last line ("Close this issue…") is the close itself | a comment ticks the line (`- [x] SEO Specialist: …`) or skips it with a reason of two or more words (`Skipped: SEO Specialist, because the client has no website`); an issue without a checklist passes |
| `cockpit:health:` (and `health:`) | nothing is left on the System health issue (the same problems it lists) | the Cockpit closes it itself when all is ok; an agent's early close reopens with the first five problems |
| `cockpit:closeout:` and `cockpit:business-review:` (0.5.0) | every checklist line is ticked, the same rule as onboarding | `Skipped: <item>, because <why>` |

The Cockpit keeps the kit's copy of the team (the state kit `registerRoleWatch` keeps in other plugins) whenever it sends `roles.updated`, and refreshes it before a check reopens an issue, so the hand-over to the Operator reaches the right agent.

## Asking the owner (`ask-owner`)

Every PiB skill's "Asking a person" section points here. One open question per issue (`asks` table, migration 003); asking again updates it.

1. The agent calls `ask-owner` on the issue it works on. The Cockpit posts the question as a comment (question, options with the recommendation first, why, steps, links), and hands the issue to the owner (roles `ownerUserId`) with status **`in_review`**. In Paperclip `in_review` is the healthy "waiting on a person" state (a board user reviewing), and an issue assigned to the owner is in their inbox; `blocked` means a dependency, not a person.
2. The question shows first in Waiting on you, in `company-brief` (`waiting`, `asks`) and in the sidebar count. After 3 days it is a health warning.
3. **The owner replies** with a comment (any board user's comment counts): the answer is stored, the issue goes back to the agent that worked on it (status `todo`; the Operator when that agent is gone) and that agent is woken with the answer in the wake reason.
4. Closing the issue resolves (done) or cancels the question; handing the issue to an agent without a reply resolves it. A reply that also closes the issue keeps the answer and leaves the issue closed. The hourly health job settles questions whose events were missed.
5. With no owner set the tool refuses with a clear message, and health warns "Nobody gets the daily brief" (fix: Setup → Team).
6. **A card must be complete (0.5.0).** Every question carries at least one link to the exact screen the owner acts on (for a plain decision, the issue itself), a grant carries steps, and an `effect` is only for a grant or a decision (never money or legal). Anything else is refused with what is missing (kit `askCardProblems`).
7. **An answer can do something (RC5, 0.5.0).** With `effect: { key, params }` a yes to the FIRST option runs the effect and checks it, and the agent is woken only when the result is in, so it never finds the grant still missing and asks again. See "Answers that do something" below.

## Company profile

Cockpit → **Profile** (`company_profile` table): legal and trading name, VAT number, address, website, booking link, sender name and email, what we sell, audience, brand voice, banned words. Owners edit any field; agents read it with `company-profile` and fill **empty** fields only with `update-company-profile` (fields an agent filled are marked for checking). The setup item "Fill in the company profile" is done once the legal name, website, sender email, what we sell and brand voice are set.

## Hand-offs, onboarding and the team broadcast

- **CRM `deal.won`** (`plugin.partnersinbiz.crm.deal.won`): recorded as activity. On a **first win** the Cockpit opens ONE onboarding issue per client (`onboarding` table, claimed before the issue is created, so re-sent events never open a second) for the Operator, else the owner (kit `routeWork` order). It is the manual's onboarding flow as a checklist: the Account Manager hand-off (client profile, retainer), ONE `ask-owner` for every grant, the SEO first sprint and the Social first month, with a deep link per switched-on module (`/crm?client=company:<id>`, `/billing?…&tab=retainers`, `/social?…&tab=accounts`, `/seo?…&tab=integrations`).
- **Billing `invoice.paid`**: recorded as activity ("INV-000012 paid in full (R 12,345.67) by Northwind").
- **`roles.updated`** carries `operatorStatus`, `reviewerStatus` and `team` (role → `{ agentId, status }`, from each plugin's snapshot `team`; a plugin may only report the roles it owns; statuses come from the agent records, a removed agent is sent as `terminated`). It is sent on team save, hourly, and at once when a snapshot changes a role's agent or status.
- Linking an agent merges plugin tool access into its one `tools:use` grant (kit `mergePluginToolsGrant`); a grant limited some other way is left alone and the step says so.

## Company memory and CRM clients

The Cockpit keeps the kit CRM projection (`crm_companies`, `crm_contacts`). ## Health

The System health issue lists bad checks at once, and **warnings unresolved for more than a day** (`health_warnings` remembers when each started; a check's own `since` counts too). The Cockpit's own checks include the owner not being set and questions older than 3 days.

### Operations watch (0.4.5)

Rules over what the host lets the Cockpit read (`public.heartbeat_runs`, `public.issues`, `public.issue_relations` and its own `asks`; the manifest's `coreReadTables` lists the three host tables). Pure rules in `src/watch-model.ts`, reads in `src/watch.ts`; `ownSnapshot` adds the checks, so they show on the Cockpit page, in `company-brief` → `health.problems` and in the System health issue. Each rule is one aggregate or a few capped rows, with times passed in from the worker's clock. A rule that cannot read its rows says so (`watch-unreadable:<rule>`, a warning) instead of checking nothing.

| Rule (check key) | Fires when | Status |
|---|---|---|
| Run rate (`run-rate:<agent>`) | more than 15% of an agent's **finished** runs (succeeded, failed, timed out; cancelled and interrupted runs are not counted) failed or timed out, over at least 20 runs in 24 hours; names the most common error code | warn, bad from 50% |
| Run streak (`run-streak:<agent>:<code>`) | the same `error_code` on the agent's latest 3 or more finished runs in a row (24 hours; a success or another code ends it) | bad |
| Retry storm (`retry-storm:<issue>`) | one open issue with 4 or more failed runs in 24 hours whose latest run also failed; names the issue, the agent, the error code and the latest error text (for example `spawn E2BIG`) | bad |
| Blocked (`blocked-no-way-out`) | issues blocked for more than 24 hours with no `unblockDescriptor`, no open blocker issue (`issue_relations`), no open question to the owner and no person assigned; lists the oldest five with the full count | warn (its own `since` is over a day old, so it reaches the issue at once) |
| Stalled (`stalled-in-progress`) | `in_progress` issues (not updated for an hour) whose idle agent assignee has had no run for 12 hours and has none queued or running; paused or errored assignees have their own agent entries | warn, reaches the issue after a day |

- **Counts:** `listRuns` (the worker side: scorecards, the brief, the watch rules) is a `GROUP BY agent_id, status` over all runs, not the first 1,000 rows, so a busy company (1,400 runs a week) is counted in full. The Overview page still reads its runs through `ui/api.ts` (`fetchRuns`, `limit=500`), so its per-agent "runs in 7 days", activity groups and runs chart undercount a very busy company until `cockpit.load` returns the aggregate counts.
- **Redaction:** the latest error text in a retry storm (and an unreadable-rule message) goes through `redactSecrets` before it is copied: `user:password@` in URLs, GitHub, Slack, API and AWS keys, bearer tokens and `token=`, `secret=`, `password=` pairs.
- **Routines:** a managed routine whose latest firing created no issue (`routine:<key>`, bad) is reported by the kit (`routineHealth`): for the Cockpit's own routines from `ownSnapshot`, for every other plugin through `publishCockpitSnapshot`. `routine_runs` is not a table plugins may read (host `PLUGIN_DATABASE_CORE_READ_TABLES`), so the signal is the routine row: `lastTriggeredAt` set on every firing, `lastEnqueuedAt` only when the firing created or joined an issue. It sees the latest firing only (not how many failed in a row), cannot read the run's error text (the check says where to look), skips paused and activity-gated routines, and waits for the next firing after the routine was edited. The likely cause comes from the issue template the host dispatches from (the routine's stored binding, `managedByPlugin.defaultsJson`), so it also names a routine that still holds an old template after its manifest was fixed; it falls back to the manifest. A firing the host skips because the routine's project is paused looks the same: the kit reads the project when the plugin may (`projects.read`, not the Cockpit) and leaves a paused one out, otherwise the detail mentions it.
- **Who may do what about a failed routine (host rules).** Any agent of the company may read its runs (`GET /api/routines/{id}/runs`). Running it (`POST /api/routines/{id}/run`) is allowed only for the routine's assignee or the board: the host answers 403 for any other agent. So the Operator runs the Cockpit's own two routines itself and, for another agent's routine, opens an issue for the assignee ("Run <routine> once now and report"); the check also clears at the next scheduled run. Plugins can run their own routines (`ctx.routines.managed.run`); a plugin tool that does so would let the Operator clear the check directly, but none exists yet.
- **Scope:** the hourly job visits only companies with saved Cockpit settings (host rule), so a company without them is not watched here.

| Check (key) | Fires when | Status |
|---|---|---|
| Role drift (kit `roleDriftCheck`) | a staffed agent lacks a role's skill or has no plugin tool access (`tools:use`) | warn |
| Run profile (`agents:run-profile`, kit) | a claude_local agent has no pinned model or run timeout | warn |

KPIs added: `ai_spend_7d`, `review_coverage`, `improvements_open`, `goals_on_track`. Quality: `memory_feedback_signal`. Needs-you additions: failed answer effects, the memory-grant item (until the Cockpit's own question is open), and what the kit's `waitingBacklog` finds.

## Close-out reviews (0.5.0, Q2-1)

Finished work is reviewed once. The Cockpit opens **Close-out review: <work>** for the Operator (origin `plugin:partnersinbiz.cockpit:closeout`, id `cockpit:closeout:…`) with the data already gathered and a checklist. Pure rules in `src/closeout-model.ts` (`CLOSEOUT`), reads and issue creation in `src/closeout.ts`, table `closeout_reviews` (the claim row is written first, so a re-sent event never opens a second issue).

- **Ways in:** `project.updated` with `status` changed and the project `completed` (the host fires it only on an explicit project PATCH); `issue.updated` when an epic's last issue closes (root done, at least 3 issues under it, all closed); the daily `closeout-sweep` for what events missed. A project with at least 3 issues, all closed, quiet for 3 days is finished. An evergreen project (40 or more issues, or work spread over 6 weeks or more) gets a **milestone** review for every 40 issues closed since the last (and at least 14 days after it), or 30 days with at least 5 closed (the 14 day gap keeps a busy project, Hunt and Gun closed 90 issues in five days, from asking for a review every day). Only real work is counted: issues from routine runs, the watchdog and plugin housekeeping (`plugin:*:operation`, such as the LLM Wiki's, which closed 156 in five days) are left out of every close-out count, so a project made of them is never reviewed. The first sweep only records a baseline for an evergreen project, so a first deploy does not flood. At most 3 reviews per company per sweep, nothing finished more than 45 days ago, one per project or epic and period. Tool `open-closeout-review` does it by hand: `projectId` is a project id or its exact name, `issueId` an issue id or an identifier such as `PAR-12` (it says plainly when neither matches, or two projects share the name).
- **Data:** issues done and cancelled, runs, failures, retries, continuation wakes, comment reopenings, blocked days (`blocked_transition_at`), wall time, run time (median and p90), tokens, notional spend and cost per issue, plan-limit failures, and each agent's spend, runs and skills.
- **Checklist:** read the evidence, decide what to change (each change recorded with `improvement-propose`), record what was learned, close the project, close the issue. The done-check reopens a review closed with lines unticked.

## Improvements ledger (0.5.0, Q2-3 and Q2-12)

`improvements` table, `src/improvements*.ts`. An improvement is a change to how the system or an agent works, with a baseline, a target, an owner and a re-check date.

- **Tools:** `improvement-propose` (the baseline is measured for a metric the Cockpit reads; the target must be on the better side), `improvement-list`, `improvement-resolve` (`resultValue`, `drop`, `archiveFact`).
- **Metric keys** (`src/metrics.ts`, one reader so a number means the same everywhere): `company:<metric>` (failure and retry rate, notional spend per day and per finished issue, issues finished, review coverage and latency, plan-limit failures, blocked and unassigned issues, open questions and the age of the oldest, memory feedback coverage, pinned tool facts, agents in error), `agent:<id>:<metric>`, `kpi:<plugin>:<key>` (a number a module reports) and `manual`. An unreadable metric gives no value and a note, never zero.
- **Daily `improvements-recheck` job** (`40 4 * * *`): measures again every improvement whose date has come and writes **improved**, **no change** (within 5%) or **worse** with both numbers. An unreadable one stays open and is retried; a manual one is **overdue** 3 days after its date. The weekly retro and `company-brief` → `improvements` list open and overdue ones; health has `improvements:overdue`.
- **Pinned tool facts (Q2-12):** a pinned (or much-used) company-wide fact that describes how a tool behaves becomes an improvement ("Fold into the <module> skill: …", at most 3 a day, not again for 60 days) tracked by the metric `company:pinned_tool_facts`; resolving it with `archiveFact` archives the fact once the skill carries the rule, also after the daily re-check has already recorded its verdict (the verdict stays; the re-check does not wait for the skill change). A fact naming a client is not a tool fact.

## Memory feedback signal (0.5.0, Q2-7)

Zero feedback after 199 briefs was read as "no complaints". `src/memory/signal.ts` turns the counts into a level: fewer than 10 briefs or under 20% with any feedback is **thin**, none is **NO SIGNAL**. `memory-review` returns `feedbackSignal`, the Memory tab shows the coverage, the weekly retro text says never to count silence as good news, and a memory brief ends with a prompt to call `memory-feedback` (migration 004 adds the kind `helpful`, so "everything helped" leaves a trace). ## Measurement layer (0.5.0, Q8-3, Q8-8, Q9-12)

`src/measure-model.ts` (pure), `src/measure.ts` (reads of `heartbeat_runs` and `issues`), tool `measure-report`, health and KPIs above.

- **Notional USD** is `usage_json.costUsd` of each run: what the tokens would cost at list price. It is **not billed**: Claude runs on a flat plan and record 0 in `cost_events`, and agent budgets count billed cents, so a budget on the flat plan never fills and says nothing about load. The Cockpit says so wherever it shows a dollar figure (`BUDGET_MEANING`).
- **Per agent, project and issue tree** (a recursive read up to the root issue): runs, tokens (in, out, cached), run time (median, p90), retries (`retry_of_run_id`), continuation wakes, why runs were cancelled (`error_code`), failures by code, runs that hit the plan limit (the "terminal limit failure" text), cost per finished issue, comment reopenings, blocked days.
- **Review coverage** is defined in code (`REVIEW_COVERAGE_RULE`): a done Developer or Senior Developer issue is reviewed when its execution policy has an approved review stage, or an issue assigned to a Reviewer or Code Reviewer is linked to it (a child, a blocks relation, or its identifier in the title or description). Latency is that review issue's created-to-completed time. It is a KPI and a warning below 70%.
- **Compact per-agent measures:** `company-brief` and `agent-scorecards` carry a `measures` block for every agent that ran. A field that is zero, empty or unknown is left out (no `retries` means none, no `failures` no failed run, no `usdPerDone` no finished issue) and cancellations and failures list the three most common reasons, so about 28 agents cost the Operator far fewer tokens. The full numbers are in `measure-report`. A plan-limit failure is the adapter's "terminal limit failure", "usage limit" or "hit your limit" text; a generic "rate limit" (a GitHub or other API throttle) is not counted.
- **Notional-spend alerts** do not depend on `cost_events` or `cost_cents`: settings `notionalDailyUsd` and `notionalWeeklyUsd` (blank means none) and the "twice the usual" rule.

## Credentials register and what only the owner can confirm (0.5.0, critic)

- **Register** (`credentials` table, tools `credential-list` and `credential-record`, `src/credentials*.ts`): names and places, owner, expiry, how to rotate, last check. ## Acceptance on the canary client (0.5.1, Q5-1, Q5-2)

An optional **Acceptance** agent uses the product the way a customer would, on the canary client only (`company:canary-<hash>`, addresses `@canary.invalid`), so a release that passes its tests but does not work is found by us. Files: `src/acceptance-model.ts` (pure: journeys, expectations, the guard, the report), `src/acceptance.ts` (worker), `src/acceptance-tools.ts`, `src/acceptance-role.ts`, `src/journeys.ts`, `journeys/*.json`, skill `pib-acceptance` (`src/acceptance-skill.ts`).

- **Journeys are versioned files**, `journeys/<key>.json`: the steps, the tool and input of each, what the Cockpit checks in the answer, the evidence a step must attach, and the role that owns a failure. Eight ship: `lead-capture` (nightly, release, on demand; looks at the form page, sends a test enquiry, checks the lead arrived, qualifies and marks the contact, checks the lead issue was closed), `quote-to-invoice`, `email-sequence-dry-run`, `social-draft-review`, `seo-sprint-draft`, `client-report` (release and on demand; they open approvals, so they never run nightly) and, from 0.6.0, `esign` and `site-events` (release and on demand; see below). `tests/journeys.spec.ts` checks every tool and parameter against the plugins' own manifests, so a renamed tool fails the build before it fails a night. A journey change is a pull request into `development` that bumps its `version`; an open run of an older version is aborted.
- **The `esign` and `site-events` journeys (0.6.0, audit Q1b-11, Q10-8, Q1b-2).** Both are `partnersinbiz.crm` journeys, so a release of the CRM asks for all six CRM journeys in one request; neither runs nightly (the nightly set stays `lead-capture`). **`esign`** (v1): `create-canary-client` (its answer must carry the lead form's page address: it proves the plugin knows its public address, which the signing page needs too), `create-sign-document` (template `proposal`, one of the canary's own people, a value in cents: the answer must say canary, a `@canary.invalid` recipient and a 64-character SHA-256), `get-sign-document` with the text (the same SHA-256, an intact audit trail, **no signing link**), `send-for-signature` (an approval, probed: it must reach the Reviewer first; the CRM refuses when it does not know its public address, which is recorded as a failure; the CRM also opens its own work issue for the document, for the deal desk, with a wake-up: the step names it, `cleanupIssues: ["workIssueId"]`, and the Cockpit cancels it with the approval when the run ends, even for a run an agent walked away from, so a rehearsal never leaves an agent waiting on it; an issue that does not name the canary is left open and the report says so), `verify-sign-document` (ok, at least two trail rows), `list-sign-documents` (the document waiting; e-sign allowed only because it is the canary), `void-sign-document` (the document and its approval withdrawn, `emailsWithdrawn` at least 1), `get-sign-document` again (void, trail still intact, no link) and `cleanup-canary`. **`site-events`** (v1): `create-canary-client`, `create-event-key` (client and label only: no site, so nothing can be pointed at a real site; only the snippet is returned and nothing is installed), `site-events-report` (the counters before), an `http` step that runs the curl the tool itself returned (one page view for the canary's own key, evidence `curl`), `site-events-report` again (`entrances` and `pageviews` must be above the readings taken before: the counter moved), `list-event-keys` (counted at least 1, refused 0, the canary's), `update-event-key` (paused; an agent may pause, only a person revokes) and `cleanup-canary` (which removes the key and its counts). **What is not scripted, said plainly:** the signature and the invoice it makes, and the signing page loading. The CRM has no dry-run signature (its "dry run" is only that an approved email to a `@canary.invalid` address is not queued), the page does not exist until a person approves the email (the signing address is proven indirectly: `send-for-signature` refuses without it), and the nightly `lead-capture` journey already loads a page from the same public static route. The signing email is an approval and the Acceptance agent never approves one; the signing page refuses a signature made from the server itself; and a link exists only after a person approves. So the CRM canary reference's Sign step stays a person's (approve the canary's email, open its own link from `get-sign-document`, sign, then check `verify-sign-document`, the deal moving to won and the draft invoice Billing makes), and Billing's side of it is covered by Billing's own tests (0.7.0). A canary tool that records a dry-run signature would let a journey cover it; that is a CRM change (see "Needs elsewhere" under Deploy 0.6.0). Neither journey sends anything, installs anything or uses a real address, and the run's own cleanup removes everything they made.
- **Tools.** `acceptance-run` (`list`, `start`, `next`, `record`, `abort`) and `acceptance-report` (a run, a journey's latest or every journey's; `file: true` files a lost report and failure issues again, once). The agent makes the plugin call and records what it passed and what came back; the Cockpit checks it against the step, looks up what it can itself (the issue exists and is done, an approval reached a Reviewer or a person, a screenshot file exists in `/tmp`, `/var/tmp` or `/home/paperclip` and is 2,000 bytes to 12 MB) and fails a step it cannot confirm.
- **Safety.** `start` refuses any client that is not `company:canary-<hash>`; a recorded input that holds a real address or another client aborts the run (aborted is neither a pass nor a failure); a tool or http step that the journey gives input to **fails when it is recorded without that input** (the guard only sees what it is told, so a call nobody can check is not a pass), and the run keeps a redacted, capped copy of the input (anything under a secret-looking name or that looks like a credential is blanked, at most 1,500 characters), never the raw one; at the end the Cockpit cancels the canary's own approvals (an approval that does not name the canary is left for a person); journeys use draft and dry-run modes only. The walls that really stop a send are the CRM and Billing canary flags; this is the second lock. The canary's won deals and paid invoices are left out of onboarding, activity and revenue (`isCanaryClientRef` in `src/onboarding.ts`).
- **Triggers.** A **nightly** job `acceptance-nightly` (`40 2 * * *`) first ends any run nobody has touched for two hours (aborted, its canary approvals cancelled, its report written, so an agent that died after an approval step leaves nothing in the owner's queue; the next start of the same journey does the same), then opens one request issue for the Acceptance agent (journeys marked nightly only). A **release**: the host emits no plugin-upgraded event to plugins, so the Cockpit reads each plugin's setup-status `version`: a version different from the last seen opens one request for the journeys that exercise that plugin (the first sighting only records it, so a deploy does not start everything at once; a rollback counts as a release of other code; the key is `release:<plugin>:<version>`, so a re-sent status opens nothing twice; the lag is up to an hour, the setup-status cadence, and the Cockpit's own release cannot trigger itself). **On demand**: action `acceptance.request` (board users, `{ journeys? }`).
- **Reports.** The report is a comment on the request issue; a failure also opens one issue per failed step, routed to the role that owns the step (`routeFromRoles`, falling back to the Operator then the owner), under the report issue. **A step that keeps failing is one open issue**: while an issue for the same journey and step is still open, a later run comments on it ("Failed again in run ...", with the checks that failed) and does not open or wake anyone again; once it is closed, the next failure is a new issue (`originId` `cockpit:acceptance:fail:<journey>:<step>:<run>`). Uncalibrated journeys will fail on first runs: fix the journey file, not the product. Health: `acceptance:failing` (warn for a day, then bad) and `acceptance:stale` (a nightly request nobody worked), a KPI "Acceptance journeys passing", and a Setup item `acceptance_agent` (optional). Silent when no Acceptance agent is staffed.
- **Staffing.** Until the kit has an `acceptance` TeamRole (see "Needs elsewhere" in the deploy notes) the agent is linked with `cockpit.link-agent` (`{ role: "acceptance", agentId }`; `cockpit.unlink-agent`, `cockpit.resync-agent`), or hired with `cockpit.hire-options` / `cockpit.start-hire` (`role: "acceptance"`). Linking syncs its skills and grants plugin tool access. A Sonnet run profile, one concurrent run.

## Skill evals and the gate (0.5.1, Q5-3, Q2-11, Q10-5)

Golden scenarios for the Cockpit's own skills. A scenario is a made-up situation plus a task; the agent answers **on paper** as a JSON plan (tool calls, API calls, comments, escalations) and a plain-rule grader checks it: tools and arguments required, tools forbidden, order, step limit, phrases that must or must not be said. Nothing real is touched. Files: `src/eval-model.ts` (pure: scenario format, prompt, plan extraction, grader, gate rule), `src/eval-scenarios.ts`, `evals/*.json`, `src/evals.ts`, `src/eval-tools.ts`, table `eval_results`, `evals/results.json`.

- **Seed scenarios (13):** Operator (a blocked issue with no way out, a routine that failed on a plugin bug, a memory grant already asked, a delegation ask that must carry its effect), Reviewer (pass and hand over, changes needed with the fix, a late review of an outward approval), the manual (invoice through approval, a login only the owner can give, hand-off to the owning role, looking at the page you changed), and Acceptance (refuses a real client, reports a failure without working around it). Each carries a right and a wrong example answer; `tests/eval-scenarios.spec.ts` proves each can pass AND fail, names real tools and parameters, never shows the agent what the answer must contain, and is fair (the skill tells an agent what the answer needs).
- **A skill version is its content hash** (markdown plus references). Results are stored per hash and per scenario hash, so changing a scenario starts its own history.
- **Running them.** A plugin worker has no door to the host's skill-test harness (a REST API with its own policy action `skills.test`), so `skill-eval` `plan` hands the Operator the exact requests, and `record` grades what the harness produced: the Cockpit reads the harness issue (origin `skill_test`, the scenario's marker in its prompt, status done) and its `output` document itself (capability `issue.documents.read`); the agent never says what came back. `record` grades each run once, and refuses a run that did not test the skill it is recorded for: the host titles the task `Skill test: <skill name>`, so a run of the live skill and a run of a candidate's test copy (named `<slug>-candidate-<first 6 of its hash>`) are told apart. It also refuses text the company is not actually running. **That is the host's own drift verdict, not a text comparison**: the host stores a plugin skill with a `key: "plugin/<plugin>/<skill>"` line added to its frontmatter, so the company's SKILL.md is never byte-for-byte what the plugin ships (the first version compared the two strings and so refused every live `record` and `baseline`). `skills.managed.get` returns `defaultDrift` (the files whose stored content differs from what the plugin declares, reference files included); only a host that reports none falls back to comparing SKILL.md with that key line taken out of both sides. `tests/helpers/host-skills.ts` is a copy of the host's storage logic (checked against its source and the live `company_skills` rows), and the fake host answers with it, so a test can no longer pass on text the host would never hold.
- **Baseline and gate.** `skill-eval baseline` (Operator only) marks the live text's results as the one to beat. Only live-mode results count toward it (a candidate's results for the same text were run on a test copy), and it clears the old baseline and sets the new one in one statement that changes nothing when there are no live results to flag, so a baseline can never be dropped for nothing. `skill-eval gate` is the rule the deploy calls: **no skill version ships if a scenario that passed at the baseline now fails, if fewer than 80% of a skill's scenarios pass, or if its scenarios were not run on this text** (`candidateHash` gates a proposed text before it is merged; a candidate is run as a separately named test copy, never under the real name). Offline, the gate is `evals/results.json` read by `tests/eval-gate.spec.ts` (`pnpm eval:gate`, and inside `pnpm test`, so the deploy's existing gate runs it): a skill whose text changed since its baseline needs recorded results (or a waiver naming who accepted the risk). It starts with `"enforce": false`: until a baseline is committed there is nothing to hold anyone to, and it only reports. After the first baseline, commit the entry `skill-eval baseline` prints and set `"enforce": true`.
- **Limits, said plainly.** Paper answers are a proxy for behaviour, not behaviour. Candidate results are recorded by the Operator: the Cockpit ties each run to the test copy by its title, but it cannot read the copy's text, so what was installed is the Operator's word (the post-deploy live re-run on the shipped text is the backstop). Starting another run for a skill marks the earlier ones Superseded in Skills Studio; harmless, because the Cockpit reads the harness tasks, not those rows. Two paper-mode scenarios per skill is a start, not coverage.

## Skill-coach loop (0.5.1, Q10-4, Q2-4, Q2-10)

Skills are plugin-managed (`plugin/<slug>/<key>`) and overwritten at every plugin sync, so a change made in the live skill is lost. Skill changes land in plugin source as a pull request into `development`.

- **`propose-skill-change`** `{ skill, diff, file?, reason, metricKey, evidence?, sourceIssueId?, baselineValue?, targetValue?, direction?, recheckInDays?, kind? }` applies a unified diff to the shipped text (or refuses it: a hunk that does not apply or is ambiguous, over the character budget, growth over max(1,500, 15%) in one change, more than 120 added lines, a secret), records the change in the improvements ledger with the number it should move and a re-check date (once per distinct diff), and returns the pull request: branch `skill/<slug>/<date>-<diffhash>`, title, body (why, evidence, diff, the checks that ran), and the steps including the eval gate. A diff that drops a "never" rule is allowed to be proposed but is marked as needing the owner's yes first. It changes no skill, file or agent.
- **Reflection Coach.** The host's built-in Reflection Coach reads agent runs and proposes changes. The Operator's `skill-coach` reference says how to provision it (`POST /api/companies/{id}/built-in-agents/reflection-coach/provision`, board or `agents:create`), that enabling its routine is a board-only action, and how to supervise it (its proposals go through `propose-skill-change`, never a direct edit).
- **Skill policy.** `cockpit.skill-policy-plan` (board users) returns the exact body to `PUT /api/companies/{id}/skill-policy`; a plugin cannot write it and nothing is applied. Rules by priority (lowest first, first match wins): `no-edits-to-plugin-skills` (p5, deny the Coach and the Operator every mutation of the plugin-managed `skillKeys` you pass), `operator-test-copies` (p10, the Operator may create, edit, remove and test other skills: the evals' test copies), `coach-may-change-its-own-skills` (p12), `agents-may-test-skills` (p20), `agents-may-not-change-skills` (p30, deny every other agent action that changes a skill); `defaultEffect: "allow"`. `tests/skill-policy.spec.ts` validates the body against the host's own zod schema and evaluates the rules the way the host does. Both live companies had no policy, so any agent could change their skills.

- **Managed skills:** `operator`, `reviewer` and the company operating manual `company-os` (slug `pib-company-os`, canonical key `plugin/partnersinbiz-cockpit/company-os`, carried by every PiB role). A hire matches a new agent on the role's own skill only (the shared skills are on every hire).

- **Daily routine:** the Operator reads `company-brief`, fixes what it can by assigning, commenting and waking agents, and posts the **Daily brief** with `post-daily-brief`.
- **Daily brief issue:** one "Daily brief: week of <Monday>" issue per week, assigned to the owner. The previous week's issue closes when the next one opens.
- **Limits:** the Operator never approves money or legal items and never changes budgets.
- **Reviewer:** comments **PASS** or **CHANGES NEEDED**, then hands the issue back to the person. It never approves or sends anything.

Core reads (`coreReadTables`):

- `issues`, for the owner's open issues, unassigned work in the brief, open onboarding issues (Flows), blocked issues, finished work and review links
- `heartbeat_runs`, for runs, failures, usage, retries and cancellations
- `issue_relations`, for blocker issues and the trees under an epic
- `projects` (0.5.0), for project names and status: close-out reviews and effort per client

Approvals are read with `ctx.approvals.list` and agents with `ctx.agents.list`. 0.5.1 adds one capability, `issue.documents.read` (the eval harness reads the skill-test task's `output` document), and no `coreReadTables` entry.

## Develop

```bash
export PATH="$HOME/.nvm/versions/node/v22.19.0/bin:$PATH"
pnpm test && pnpm typecheck && pnpm build
```

Tests that touch SQL run on a real embedded Postgres under the host's SQL rules (`tests/helpers/pg.ts`, a replica of the host guard; set `COCKPIT_SQL_DUMP=<file>` to dump every runtime statement so the host's real guard can be run over them). `tests/helpers/hybrid.ts` joins that database with the in-memory fake host and the real `registerCockpit` wiring (jobs, events, tools, actions, ask effects). Specs that need Postgres skip when `embedded-postgres` is not installed: read the Test Files and skipped counts of a run (996 tests in 54 files, none skipped, at 0.6.0), because a skipped `*.pg.spec` is a silent hole. `tests/journeys.spec.ts` reads the working-tree manifests of CRM, Billing, SEO and Social to check every journey tool and parameter, so this suite depends on those plugins' sources being in the tree (a tool the journeys name that no manifest declares fails the build); since 0.6.0 it also reads the CRM's e-sign, site events and canary source for every result field the two new journeys expect, capture or clean up after (a renamed field fails the build, not a night). `tests/helpers/host-skills.ts` mirrors how the host stores a managed skill (see Skill evals). **Migration comments must not contain apostrophes**: the host's SQL guard (and its replica in `tests/helpers/sql-guard.ts`) reads one as the start of a string and rejects the migration as "DDL or backfill only" (15 specs failed on this in 0.5.1). Never edit an applied migration; `tests/helpers/pg.ts` `reset()` must list every new table. `pnpm eval:gate` runs the offline skill gate on its own.

## Deploy (0.5.0, kept for the record)

Stop first: the manifest gains capabilities (`goals.read`, `goals.create`, `goals.update`, `access.members.read`) and `projects` in `coreReadTables`, and the host reads both at startup. Order (see `packages/plugins/DEPLOY.md`): back up, stop Paperclip, `deploy-plugins.sh`, start, verify; migrations 004, 005 and 006 apply on start (DDL only; 001 to 003 are untouched). Then sync the skills for every company (`cockpit.load`, or wait for the hourly sweep). Nothing here needs a setting to start working; the optional settings are `notionalDailyUsd`, `notionalWeeklyUsd`, `usdRate`, `effortAlertRatio`, `credentialChecks.<provider>` and `credentialSeed`.

- **`credentialSeed` (owner company only).** The 22-row starting register describes Partners in Biz's own servers and tokens. It is loaded only for a company whose Cockpit settings tick **Load Partners in Biz's own credentials list**, which defaults to off: tick it on the PiB company (PAR) and nowhere else, then the next daily `credentials-check` (or tomorrow's run) seeds it. A client company (PARA, any new one) that saves its settings gets an empty register and no "exposed credentials" warning. Saving a company's settings is safe at any time after this version is deployed.
- **The managed routines do not pick up new description text.** The host's `routines.managed.reconcile` does not update the description of a routine that already exists; only a reset does (an owner-approved action). So the live "Daily operations review" and "Weekly retro" keep their old step lists until reset, and the new steps (measure report, improvements, close-out and business reviews, credentials) reach the Operator through the updated skill and its references, which is how the Operator already works. Reset the two routines (`routines.managed.reset`, an owner-approved action) only if you want the new steps in the routine's own text.
