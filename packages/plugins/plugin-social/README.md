# Social

Paperclip plugin `partnersinbiz.social`: connect social accounts, draft posts with media and per-platform overrides, approve them, and publish on schedule with retries.

## Scope: own work or one client

Every account, post, media asset, RSS feed and inbox item belongs to one scope: PiB's own work (no client) or one CRM client (a company, or a contact for sole traders; `client_kind` + `client_ref`).

- `/social` shows own work only. A client's social work opens from the CRM client workspace as `/social?client=company:<id>` (or `contact:<id>`), with the shared workspace bar on top. New accounts, posts, media and feeds belong to the page's scope; tab changes and the OAuth return keep `?client=`.
- Scopes never mix: a post only targets accounts and media of its own scope (checked on create/update/attach, before scheduling, and again by the publish job).
- An account moves scope from its Edit dialog ("Belongs to"). The move is refused while unpublished posts of the old scope still target it; its inbox moves with it and the old scope's feeds stop drafting to it.
- Agent tools take `client` ("company:<id>"/"contact:<id>") or `clientKind` + `clientRef`; omitting it means own work. Issues for client work are titled `[<client>] …`.
- `GET /api/plugins/partnersinbiz.social/api/client-summary?companyId=&kind=&id=` (board auth) returns `{ headline, stats }` for the CRM workspace.

## Setup

1. Settings → Plugins → Social, for the company: set **Public base URL** (e.g. `https://paperclip.partnersinbiz.online`), a **token encryption key** (secret, 16+ characters), the platform client ids/secrets and the R2 block. Click **Save** (jobs cannot act for a company without a saved config row).
2. Open the Social page once, then register the redirect URI it shows with every OAuth provider:
   `<publicBaseUrl>/_plugins/<plugin installation id>/ui/oauth-callback.html`.
   The host serves plugin files only by installation id (not by plugin key); the id changes only if the plugin is uninstalled and installed again.
   Connect accounts only from the public base URL's own address. The pending sign-in lives in the browser's localStorage and the session cookie is per host, so a sign-in started on another address (for example the sslip.io host) cannot finish there. Since 0.8.2 the Social page says so and keeps the Connect buttons off on any other address.
3. R2 bucket CORS must allow the Paperclip origin to `PUT` with a `Content-Type` header.
4. **Setup → Team → Social agent**: hire one or pick an agent you already have, then Resume it once its adapter has a working model key. See "The Social agent" below.

## LinkedIn company pages

To post to LinkedIn company pages and manage their inbox, set up a second LinkedIn app with the Community Management API (separate from the personal LinkedIn app that handles individual profiles):

1. In **Settings → Plugins → Social → Platforms → LinkedIn Pages app (Community Management API only)**, add the client ID and client secret. The app requires these scopes: `w_organization_social`, `r_organization_social`, `rw_organization_admin`.
2. Register the same redirect URI as other apps: `<publicBaseUrl>/_plugins/<plugin installation id>/ui/oauth-callback.html`.
3. On the **Accounts** tab, click **LinkedIn Page** to connect company pages. The personal LinkedIn app (personal profiles) and the Pages app are separate; connecting a personal profile uses the first app, company pages use the second.
4. Accounts saved from the Pages app carry `meta.app = "linkedinPages"` and are refreshed, published to, and have their inbox polled with the Pages app credentials. The personal app (meta.app unset or `"linkedin"`) is untouched.
5. The deprecated **LinkedIn company pages** toggle (`linkedinOrgPages`) is ignored; remove it when upgrading.

## The Social agent

The plugin never creates its agent. Every agent is hired the same way, through a normal Paperclip task:

- **Hire** (in Setup → Team; `social.hire-options` for the draft, `social.start-hire` to open it) creates a task prefilled with the hire request (`src/hire.ts`: name "Social Media Manager", role `general`, adapter `hermes_local` then `claude_local`, skills `pib-social-publish` + `pib-social-content`, budget $0, a short AGENTS.md). The person picks the assignee (usually the CEO / hiring agent, or themselves) and a task is created with `originId: hire:social-media-manager`.
- When an agent matching the spec appears (created after the task, with a social skill or the name/title "Social Media Manager"), the plugin links it automatically: on `agent.created` / `agent.updated` / `agent.status_changed` / `approval.decided`, on the Social page load, and from the hourly `refresh-tokens` job. It comments on the hire task with what it did.
- **Pick / change / remove** in Setup → Team links any agent by hand (for example an existing "Outbound & Social Specialist") or forgets the link. The worker cannot attach skills to an agent it did not create; the Social page attaches `pib-social-publish` / `pib-social-content` for the person viewing it.
- **The Social page** (Overview) shows an agent box only when something is wrong: no agent and no open hire, a hire open without an agent, the agent paused, in error or waiting for approval, or a social skill missing. One line plus **Fix in Setup** (Setup → Team); a missing skill also gets **Attach skills** and **Re-sync**. When the agent is fine the page shows nothing.
- Wiring a linked agent (`wireAgent`): gives it plugin tool access with the kit's `mergePluginToolsGrant` (the host keeps one `tools:use` grant per agent: it is widened, never duplicated; a grant limited to named tools is left alone and the steps say what a person must do), reconciles the Social project and assigns the weekly "Weekly social review & plan" routine (key `plan-next-week`) to it (an existing routine owned by another agent is reassigned and keeps its status). The routine ships active with its Monday 07:00 trigger on; if a person pauses either, Setup's "Switch it on" link (`/social?routine=on`) switches both on again in one click as the board user. Failed posts, the daily reply queue, repurpose tasks and approved posts without a time go to the linked agent from then on (kit `routeWork`: else the Operator, else a person).
- **Re-sync** (`social.activate-agent`) wires the linked agent again. Agents activated before 0.4.0 (host-managed from the manifest `agents` declaration) are still found through `ctx.agents.managed.get` and keep working.
- Actions (people only): `social.hire-options`, `social.start-hire`, `social.link-agent` `{ agentId }`, `social.unlink-agent`, `social.activate-agent`. The link lives in plugin state (`pib-hire` / `role:social-media-manager`, company scope).

## How it works

- OAuth returns to a static bridge page (`dist/ui/oauth-callback.html`) that posts the code to `POST /api/plugins/partnersinbiz.social/api/oauth/complete` with the board session.
- Tokens are sealed with AES-256-GCM (kit `sealJson`) under the configured key; a missing key fails closed.
- Jobs: `publish-due` (5 min, retries 1/5/15/60 min, 5 attempts), `refresh-tokens` (hourly), `collect-metrics` (30 min), `poll-inbox` and `poll-rss` (15 min), `score-posts` (daily 03:25), `measure-experiments` (daily 03:50), `redeliver` (10 min) and `client-answers` (5 min, 0.8.0). Every job takes company ids from its own rows and passes them explicitly.
- One post targets many accounts. Organisation posts cannot use a personal account. Who approves a post is the scope's approval policy (0.8.0): by default a team member, who clicks Approve; for a client it can be the client, on a link. The Social agent never approves; a delegated approver a person named for the scope can, after a scored Reviewer pass (0.10.32). (Where only the client approves, the client's link is the approval and an agent holds it: see "The client's link is a bearer token" below). Approval schedules the post at its proposed time (see 0.6.0).

## Jev inbox triage (0.5.0)

Settings → Social → **Jev decisions**: pick the TypeSafe API key secret (the same one in every PiB plugin), keep the pinned model, leave **Use Jev** on. Without a key the built-in keyword rules triage the inbox instead (0.6.0, below).

- After each `poll-inbox` run (and for items recorded by hand) every new item gets **one** Jev call with only `platform`, `kind`, `text` (600 characters at most) and `post` (the caption it is on, 200 at most). Questions: `needs_reply` (noul), `intent` (question / complaint / praise / lead / spam / other), `sentiment` (negative / neutral / positive), `escalate` (legal, safety or PR risk).
- Actions: spam with confidence ≥ 0.7 (kit `update`) → marked read. `escalate` yes (≥ `read`) → an issue for a person (the post owner, else the account's creator, else the company's default person); the item is not queued for the agent. `needs_reply` yes and not spam → one issue **per account per day** for the Social agent ("Reply to social comments: …"); later items that day are added as comments and wake the agent.
- The answers are stored on the item (`inbox_items.triage`) and logged in `decisions` (kit `decisionsMigration`), with `acted` set on the answers the plugin acted on. The inbox shows chips; **Fix** corrects an answer (kit `correctDecision`, labelled data for later). Correcting a spam item to anything else brings it back to `new`.
- Failed calls are retried on the next poll; on the last of 3 tries the built-in rules triage the item, so nothing is left untriaged.

## Growth Lab (0.5.0)

An autoresearch-style loop per scope (own work, and each CRM client), channel `social`, on the kit `experiments.ts` tables (`growth_programs`, `growth_playbook_versions`, `growth_experiments`, `growth_experiment_items`) plus `post_scores`, `post_features` and `growth_playbook_changes`.

- **Program**: created on first use with the kit starter playbook. Goal and metric default to "engagement rate lift at 7d". Autopilot: `off` (agents only read), `safe` (default: agents propose, a person approves experiments and keeps or discards playbook changes), `full` (proposals start at once, the agent may decide changes, wins are kept automatically). Topics, brand voice, platforms and cadence are set on the **Growth** tab.
- **`score-posts`** (daily): for every destination with a 7-day snapshot, kit `engagementRate` (reach, else impressions, else views; none → not scored), baseline = median of the same account and platform over the 30 days before it (its own post excluded, at least 3 earlier posts), lift = rate ÷ baseline − 1. Then feature tags once per published post: format, length and posting daypart in code; hook, CTA, topic (only when the program lists topics) and tone from **one Jev call with the caption only** (1000 characters at most); plus the program's own questions. A new question backfills posts from the last 90 days with one call per post asking only the missing keys. Without Jev only the code features are stored.
- **Experiments**: `propose-experiment` (one variable, `hypothesisType` like `hook:question`, arms `control`/`variant`, `minPerArm` default 3, 7-day window). At most 3 running and 3 proposed per program. On `safe`, proposals and playbook changes go into **one approval issue per program per ISO week** (assigned to the program owner, the last person who saved its settings, else the company's default person); it closes itself when everything on it is decided. Posts carry `experiment_id` + `experiment_arm` (`experimentId` + `arm` on `create-post`/`update-post`, and an Experiment select in the composer).
- **`measure-experiments`** (daily): once every tagged post is published and scored and each arm has `minPerArm` scores, or 21 days after it started, kit `experimentVerdict` on the arms' lifts (compared as ratios to the account's usual level, so a control median of 0 lift still gives a meaningful change). The verdict goes into the program scoreboard (kit `recordVerdict`); a win adds a rule to "Rules we follow", a loss to "Things that did not work", as a pending playbook change. Keep → a new playbook version; discard → logged.
- **Agent tools**: `performance-review` (top/bottom 5 posts with features and lift, kit `featureLifts`, running/proposed experiments, pending changes, hypothesis types ranked by kit `rankHypothesisTypes` UCB), `get-playbook`, `propose-playbook-change`, `decide-playbook-change`, `list-experiments`, `propose-experiment`, `approve-experiment`, `reject-experiment`, `propose-feature-question` (add or retire; at most 12 of its own).
- **Growth tab** (own page and client workspace): stats, what waits for a decision, the playbook (markdown, version history, edit), experiments, UCB ranking, feature lifts, top and bottom posts, feature questions and program settings.

## 0.7.2

- **The weekly routine runs again.** Releases up to 0.7.1 declared the routine's `issueTemplate` as `{ originId: "routine:plan-next-week" }` with no `surfaceVisibility: "plugin_operation"`. For such a template the host opens the run's issue as `routine_execution` with that string as its origin id, then looks the run up with it in `routine_runs.routine_id` (a uuid column) and fails the dispatch: the routine's only run (2026-09-28) failed and every Monday would. The manifest now declares no template, so the host uses the routine's own id as the origin id, which is also what the Routines page reads to show a routine's live issue. A test rejects any managed routine that declares an `originId` without `plugin_operation`.
- **Existing companies are repaired automatically.** The host reads a routine's issue template from the binding it stored when the routine was reconciled (`plugin_managed_resources.defaults_json`), not from the manifest, and rewrites the binding only on `routines.managed.reconcile`. `healPlanRoutine` (`src/routine-template.ts`) reads the binding, and when it still holds the old template calls `reconcile` (which touches nothing but the binding) and reads it back. It runs once per process for each company the plugin serves (the first action, tool call, page load or hourly job after a worker start), is retried every ten minutes while the host still reports the old template, never creates the routine, and never throws. Setup → Team → Re-sync of the Social agent does the same through `wireAgent`.
- **The Cockpit finds the weekly plan by the routine's id.** `draftWork` looks the managed routine up (`ctx.routines.managed.get`) and lists issues with that id as `originId` (the host's `routine_execution` issues). The routine's issues carry no `plan:` origin and match no done-check.
- **First plan for a scope.** The weekly routine only runs Mondays, so a scope whose first account connects on a Tuesday waited nearly a week, and a failing routine left it waiting for good. Saving an account (`saveCandidate`: OAuth, the account picker, Bluesky) and the hourly `refresh-tokens` job (for accounts connected before this release and plans that failed) now call `ensurePlanForScope` (`src/plan-trigger.ts`). A scope that has a live company or client account (connected or expiring), no post (RSS and reply drafts do not count) and no earlier plan gets ONE issue "Plan social for <client or own work>" for the Social agent (origin `plan:<own|company:<id>|contact:<id>>`, in the Social project, agent woken). The claim is a `handoffs` row (kind `plan`, key `plan:<company>:<scope>`) written before the issue, so two accounts saved together, a connect racing the sweep and a crash between claim and issue open one issue; a closed or deleted plan is never reopened. With no agent to take it nothing is claimed or opened (the next try can); it never fails a connection. No migration and no capability: it reuses the existing `handoffs` table. The issue's close is checked (`checkPlan`: a post must exist in the scope that was made after the issue opened, else it is reopened with what is missing; the third early close goes to the Operator). The Cockpit's `social.drafts` stage counts an open first plan with no draft in its scope as waiting, and stuck after two days.
- **The Social agent that cannot start is flagged.** The Cockpit health reads the linked agent's latest runs (`heartbeat_runs`, already readable) and shows `agent-runs` as bad when they all stopped at the host's workspace check (`workspace_validation_failed`), with the fix and a link to the project.
- **Known limit (plugin-managed project workspace).** A plugin-managed project cannot declare an execution workspace policy or a git workspace: the host's `resolveManagedProject` applies only name, description, status and color (the `settings` field is stored in `plugin_managed_resources.defaults_json` and never read; `ctx.projects.managed` has only `get`, `reconcile` and `reset`; the plugin has no project write or filesystem capability). With the host default of isolated worktrees for a project with no policy, the Social project (no policy, `_default` folder not a git checkout) stops every run at the workspace check. Fix it outside the plugin: PATCH the project's `executionWorkspacePolicy` to `{ "enabled": false, "defaultMode": "shared_workspace" }`, or git-initialise the project's `_default` folder (the VPS ops janitor). Social needs no repository.

### Who approves a post, and the client's own approval (Q1a-2)

Until 0.7.2 exactly one thing approved a post: a board user clicking Approve. Nobody outside the company could, and no agent has an Approve action under any policy (still true; the one caveat is a client-only policy, see "The client's link is a bearer token"). Now each scope (own work, and each client) has an **approval policy**, set by a person on Social → Posts → **Who approves** (`social.set-approval-policy`; an agent can read it with `get-approval-policy` but never change it, because a policy delegates authority). A policy lists the sign-offs a post needs:

- **A team member approves** (default: the 0.7.x behaviour, unchanged for every scope that has no policy row).
- **The client approves**, on a tokenised page, or a person records that the client approved elsewhere with a note saying how (`social.record-client-approval`). Client scopes only.
- **The Reviewer passes it first**: a check, never an approval (`record-review-verdict`, Reviewer agent only).
- Somebody always approves: the team member, the client, or both (a database check says so as well).

The post becomes approved when every sign-off its policy asks for is in **for its current version**. Each sign-off is stored with a SHA-256 fingerprint of what the post would publish (text, first comment, overrides, media, accounts, proposed time); editing the post makes earlier sign-offs stale, so nobody's yes ever covers a later edit. A team member's click is recorded as a sign-off, and where other sign-offs are still missing it says so ("Recorded. Waiting for the client's approval.") instead of approving; the post stays in review and the review issue goes to whoever acts next. Loosening a policy approves the posts whose sign-offs were already in.

**The review issue** (`review:<postId>`, one per post) follows the policy: the Reviewer first when the Cockpit has one (as before; its brief now says to record a verdict with the tool, which hands the issue on: to the person or delegated approver who approves, or to the Social agent when the client has to approve; changes go back to the Social agent with the post returned to draft and the issue kept open, so sending the post for review again reuses it). With **no Reviewer nothing opens, as before, unless the client approves**: then the Social agent gets "Get client approval for social post: ..." with the steps. (The kit asked Social to use `openApprovalIssue` here. It is not used: opening one issue per post for the owner when there is no Reviewer would flood the inbox, and the Cockpit already lists every post in review under "Needs you". Say if you want it.)

**The review issue is never the only copy of a note.** The issue is how the Social agent hears about a post, and agents close issues after drafting the email, so nothing relies on it still being open. Whenever the Social agent has to be told something (the client asked for changes, an answer arrived for an older version, a link ran out, a team member approved and only the client is left, a policy began to ask for the client after the post was already in review) the plugin reassigns the open review issue to the agent, whoever held it (an ask can leave it with the owner), and wakes it; when the issue is closed or was never opened it opens a fresh one for the same post (`review:<postId>`, same project routing) that carries the note, and the post points at it, so sending the post for review again reuses it. Saving a policy that newly asks for the client gives every in-review post that waits for an agent's step its issue (`routed` in the result). A done-check on `review:` issues reopens an agent's early close when work is left for an agent: the Reviewer's verdict is missing where the policy needs it, or the client has to approve and no link for this version is open. Waiting for a team member's click, or for the client's answer on a link that is out, is not unfinished work, so the agent may close the issue then.

**The client's link** (`request-client-approval`, an agent or a person on the page): the post must be in review, validate, the scope's policy must ask for the client, and the Reviewer must have passed this version when the policy asks for that. It freezes what the client will see (the text each account will publish, the media over https, the proposed time) into `client_approvals.snapshot`, mints a random 32-byte token and returns `https://<approval page>/<token>` with the people at the client (the CRM projection) and a ready email (subject, text, html). **Only the token's SHA-256 is stored**, so reading the table never yields a link; a link is shown once. A new link supersedes the old one. It stays open 14 days (1-60, per scope) and is held (refused) when the approval page does not answer its health check, so a client is never handed a dead link.

**The email is a Mailbox draft, never sent by Social.** By default the plugin opens a drafting task for the Account Manager (who has the mailbox delegation; the Social agent usually has none, so drafting itself would only fail) when the company has one, and says so in the call's answer; with `draft: "me"`, or when no Account Manager is staffed, the agent creates it with `partnersinbiz.mailbox:create-draft`. `draft: "account-manager"` always opens the task (for the Operator or the owner when no Account Manager is staffed, and is refused before any link is made when nobody can take it). Either way the agent asks the owner once to send it. The drafting task's text holds the live link (the SEO preview links do the same): it is the one place the link is written into issue text. Social emits no mail event. (A stronger path would be a Mailbox event that creates the draft from Social's payload, so no agent carries the link; see needs_elsewhere in the 0.8.0 report.)

**The approval page** is a small separate service, `ops/approval-server` (its own README, unit `pib-approval.service`, port 3032, `install.sh`, `setup.sql`), cloned from the SEO preview service: a tokenised page that shows the post as it will appear on each account and takes Approve (name required) or Request changes (note required) once. Its database role `pib_approval` can read the snapshot and write only the answer columns. A GET never changes anything (mail scanners cannot approve), pages run no scripts, send no referrer and are never cached or indexed. Default address `https://preview.partnersinbiz.online/a` (a `handle /a/*` in the existing preview Caddy block: no new DNS or certificate); override in settings (**Client approval page address**; it must start with `https://`, the schema refuses anything else, and a bad value saved before is shown on the Setup item and the Cockpit instead of breaking them).

**The client's link is a bearer token, and an agent holds it.** `request-client-approval` hands the link to the Social agent so it can be put in a Mailbox draft, and the agent runs on the same server as the approval page. Where a team member also approves (the default, and "team member and client") a forged answer would still need that person's click. Where **only the client** approves, the link is the approval, so whoever holds it could answer in the client's name. Mitigations in place: the page refuses an answer that comes from the server itself (its own addresses and loopback, including a call to the public address from the same machine), the agent text forbids opening the link or submitting its form, the policy card says so when "client only" is chosen, and the answer records the name typed. That is a speed bump, not a wall (a process on the server that calls port 3032 directly with a made-up `X-Forwarded-For` is not stopped). **Tell the owner before "client only" is turned on for a client**; the structural fix is a Mailbox "draft from an event" path so no agent ever sees the link (needs_elsewhere). Editing the post, attaching or removing an account, returning it to draft or approving it supersedes every open link (the accounts are part of what the client approved).

**The `client-answers` job** (every 5 minutes) applies each answer once (claimed with `notified_at`, released on failure): it records the client's verdict as a sign-off, comments on the post's review issue, wakes the Social agent and approves the post when the policy's other sign-offs are in. An answer for a version that has since changed is not applied and says so; one for a post no longer in review is kept on record. A request for changes returns the post to draft with the client's note on the issue. Links that ran out unanswered are closed and the Social agent is told once. The Cockpit shows a red check when links are out while the page is down, a warning for links unanswered over a week, a warning when a policy needs a Reviewer and none is running, and lists a post only the client approves as "Waiting for the client". Setup has an optional "Client approval page" item that turns green when the page answers.

### Autonomy inputs (Q10-10)

Every Reviewer, team member and client verdict is a row in `review_outcomes`: stage, outcome (approved or changes), round (a post sent back and forth has rounds 1, 2, 3), the post's **type** (`original`, `repurpose`, `rss` or `reply`, by format: text, image, carousel, video), its scope and platforms, how it was recorded and who. A person sending a post back from review counts as the owner asking for changes. `review-outcomes` (tool, and `social.review-outcomes`) returns first-pass approval rates and approval streaks per type and stage for one scope. **The autonomy ladder (PAR-4701) is built for low-risk posts only.** A post is auto-approved in place of the team member's click when its source is `original` or `repurpose`, its format is text or one image, its scope's policy does not ask for the client, `validate-post` passes, and the owner streak for that type in that scope is at least 5 (people's verdicts only). A required Reviewer pass still comes first. The complaint/legal/safety/PR exclusion works by source only: inbox replies and RSS items are out, but an agent-written original is eligible, because nothing reads its content. `review-outcomes` reports `autonomy.enabled` true only when some type qualifies in that scope; everything else stays with a person.

### Client issues in the client's project (Q1a-12)

Social registers the kit's `registerClientProjectWatch` and opens every scope's issue through `projectIdFor`: the nine call sites (failed post, reconnect, review, schedule task, reply digest, escalation, first plan, repurpose task, Growth Lab approvals) use the project the CRM linked to the client (`client.projects.updated`, ids only, kept in plugin state); a client with no linked project, and own work, use the managed Social project; a linked project that was archived or deleted is skipped now that the plugin may read projects (`projects.read`, new). A test fails if a call site goes back to the shared project.

### Connecting an account closes its ask (Q9-10)

`connect-account` (an agent) records the wish against the issue the agent is working on (`connect_requests`; the issue comes from its run's context, or an `issueId` param). When the connect flow saves an account (OAuth, the picker, Bluesky; a first connection or a reconnect) the matching open requests are resolved: a comment on the asking issue, the issue handed back to the agent when `ask-owner` had given it to the owner (the Cockpit then settles its ask: handing an issue to an agent resolves it), and a wake-up. The account's own "Reconnect ..." issue is closed with a note. An ask can also carry the effect **`social.connect-account`** (platform + client, whitelisted): when the owner answers "done" the plugin checks the account really is connected and tells the agent, instead of the agent finding out by trial; it changes nothing. `connect-account` returns the exact effect to pass.

### Agents can attach media they make (Q1a-5, Q10-11)

`list-issue-attachments` and `import-media-from-attachment` turn a file an agent attached to its issue into a media asset on R2 and return the **asset id** (never a link to private storage). The plugin reads the bytes through the host (`issue.attachments.read`: company-scoped, audit-logged, bytes only), checks the checksum, reads the **type from the file's own bytes** (the PARA-4 MP4s are stored as `application/octet-stream`), and reads width, height and video length so a slide that is not 1080 px or a reel that is not 9:16 is noted before a platform rejects it. JPEG, PNG, GIF, WebP, MP4 and MOV up to 64 MB (the bytes cross the host bridge as base64; bigger files go through `import-media-from-url` or a person's upload). Importing the same attachment again returns the same asset. **Social does not read a workspace path an agent names.** A plugin worker can read the server's disk, so a path from an agent could reach credential files that live under the same user; the host's workspace folder access is text only anyway. The agent attaches the file to the issue first (`POST /api/companies/:companyId/issues/:issueId/attachments`, the paperclip skill), which is also how the PARA-4 agents delivered their files. (A path import could be added later with `project.workspaces.read` and a real-path check that keeps the file inside the run's own workspace.) The type is taken from the file's `ftyp` brand, so a phone's HEIC or an AVIF is named as such instead of being passed off as a video. A client's library takes files only from that client's own projects (or the shared Social project): when the CRM has linked projects to the client, an attachment on an issue in any other project is refused, so another client's file cannot be imported by mistake (own work, a client with no linked project and an issue with no project are not checked). The bytes are decoded once into one buffer (no second copy of a file that can be 64 MB).

The social-content skill gets a **Media studio (pib-media-studio)** section and `references/media-studio.md`: brief, the client's brand (the CRM profile's voice and tone and, when the profile's brand kit is filled in, `primaryColor`, `secondaryColor`, `accentColor`, `fonts`, `logoKey` (found with `list-media-assets` by `r2Key`) and `toneExamples`; the client's own site only fills what the profile lacks), formats and safe areas, slides as HTML rendered to PNG by Chromium (the installed one, or Playwright), videos stitched with ffmpeg, checks, then attach and import. It follows what the PARA-4 agents already did (carousels at 1080x1350, 9:16 MP4s, a safe-area template, the generator zip) and adds no provider dependency: a generation tool (Higgsfield, Seedance) is optional for backgrounds and B-roll, and without one the agent writes paste-ready prompts. Skills stay under 18,000 characters (publish 15,715, content 7,854; references carry the rest, tested).

### Erasure of a person's social data (Q10-13)

`registerEraseReceiver`: when the CRM sends an approved `contact.erase.requested` (never without `approvedByUserId`), Social finds the person's inbox items (the lead hand-offs the CRM answered with their contact id, and any item whose text or author contains their email or the last nine digits of their phone: no LIKE, no guessing from a handle) and turns them into tombstones (author and text replaced, reply text, link and triage cleared; the platform's own comment id stays so the next poll does not bring it back), deletes the Jev decisions and queued lead hand-offs for them, cleans the issues that quote them (**per issue, by what it is**: an escalation issue is about one item, so its whole text is replaced; the daily reply-queue digest lists many people's comments plus the agent's steps, so only the lines of the erased items become `- [erased]` and everyone else's lines and the steps stay; a digest the host returns shortened is never written back), and clears the client approval records that name them (the email a link was meant for, the name they typed, their note; the approval itself stays, anonymously). What it cannot or may not erase is reported as `retained`: the original comments on the platforms, issue comments that quoted them (a plugin cannot edit a comment, including the "N more to reply to" comments added to a day's digest), and published posts that mention them (the client's content). An item whose issue could not be cleaned is held back (kept, with an error saying so) so the retry finds it again: nothing is left quoting the person for good. A marketing-only erasure has nothing in Social. Idempotent, and answered once per request by the kit. The consent receiver is not wired: Social sends no marketing email.

## 0.11.0: manual accounts and posting by hand

A **manual account** is a platform account with no publishing link: the platform has not approved our app yet (TikTok), or a person wants to post there themselves. A person adds it on Accounts ("Add a manual account": platform and handle; nothing is signed in and no token is stored). It works in every space: own work, a client's workspace, and My Social.

- Posts to a manual account are drafted, validated, reviewed, approved and scheduled like any other. `list-connected-accounts` shows it with `manual: true` and `connected: true`.
- At the publish time the destination moves to `awaiting_manual` (migration 020) instead of going to a provider, and one **"Post by hand"** issue per post goes to a person (the post's owner, else who added the account, else the default person). The post stays `publishing` until then; the publish job leaves it alone.
- The post page shows a panel per such destination: copy the caption, send the media to the platform's app through the phone's share sheet (or save it), open the platform's own composer, and **Mark as posted** with the link. `composeIntent` (`platforms.ts`) builds the composer link: the text is in the box on X, LinkedIn, Threads, Bluesky, Mastodon, Reddit and Pinterest. TikTok, Instagram, YouTube, Facebook and Dribbble document no link that fills in a post, so the caption is copied and the upload page opens.
- `social.mark-destination-posted` records one destination (a person only). The post rolls up as after a publish run, and the issue closes when nothing waits. A destination whose automatic publish **failed** gets the same panel, so a person can post it themselves and settle it.
- **Skip** on a waiting destination (`social.skip-destination`) removes the account from the post. Nothing is recorded as a failure, so health counts stay true and a retry cannot bring it back. With no destination left the post returns to `approved`.
- One live task per post: a destination that waits again never reuses the id of an old issue, and a task the host refused at the publish time is opened by a later job run. Removing the last waiting account closes the task.
- A post with a published part cannot be deleted.
- A post can be hand-posted before its time; it keeps its status until the last destination is out.
- No metrics come from the platform for a manual account: agents record what a person gives them with `record-post-metrics`.
- When the platform later approves the app, connect the account the normal way and switch the manual one off. Posts already attached to the manual account stay with it.

## Metrics errors (0.10.11)

When a metrics snapshot cannot be captured, the destination keeps a `metricsError` (`at`, `window`, `kind`, optional `status`, `message`) inside its `result`, and `post-analytics` returns it per destination with `metricWindows`. Kinds: `provider` (the API call failed), `insights` (counts were stored but a best-effort sub-call such as impressions failed; the window stays open and is retried, and a later snapshot fills only the null columns), `unsupported` (LinkedIn personal profiles: analytics are not available to this app, so no call is made). A clean snapshot clears the error. Messages never contain URL query strings or tokens. The `collect-metrics` job summary adds `partial` and `errorsByPlatform`.

## Facebook insights (0.10.12)

Facebook post snapshots read `post_media_view` (stored as impressions and views) and `post_total_media_view_unique` (reach) in one Insights call, and `post_clicks` (clicks) in a second call, so a failing clicks metric cannot blank impressions or reach. A failure or missing metric is stored as `insightsError` (kind `insights`). The Facebook login now also asks for `read_insights`. A Page connected before 0.10.12 may need one reconnect; do it only when the persisted `metricsError` on a Facebook destination shows a permission error.

## LinkedIn organization statistics (0.10.13)

LinkedIn Page (organization) posts read `organizationalEntityShareStatistics` (impressions, unique impressions as reach, clicks, likes, comments, shares) for `urn:li:share:` and `urn:li:ugcPost:` posts. Organization pages only: personal profiles have no analytics. A missing element or an API error is stored as `insightsError` and the window is retried; values are never written as zeros. Needs a connected LinkedIn organization account.
